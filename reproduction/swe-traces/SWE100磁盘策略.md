# SWE100 磁盘策略变更

2026-09-19，第71题完成后，用户明确要求“不要管这个阈值了，继续执行”。第72题第一次准备在调用API之前被12GiB预构建检查拦截；原日志保留，重试使用新日志。

当前 `deepseek_swe100_config.json` 显式设置 `disk_reserve_checks_enabled=false`，关闭构建前12GiB、构建中8GiB、采集/环境验证6GiB、检查点导出前9GiB和导出中6GiB的空闲磁盘检查。其他配置省略该字段时默认保持检查。镜像准备通过 `--disable-disk-reserve-checks` 接收同一策略。

不改变固定样本、模型、提示词、轮次、预算、任务时长、容器隔离或归档大小约束。记录构建和验证实际使用的策略，并在运行日志中保存配置变更及代码哈希。历史每题记录不改写。若真实磁盘写满，系统仍会产生I/O失败，不能保证未完成写入可恢复。

只在环境信息归档后释放本实验临时镜像；不清理下载缓存，不操作其他用户资源，也不删除受保护的原始镜像或当前必需环境。

第72题随后完成镜像构建，但验证时OpenBLAS按宿主机CPU数量尝试启动128线程，触及容器进程/线程限制。自此将 `OPENBLAS_NUM_THREADS`、`OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`NUMEXPR_NUM_THREADS` 设置为已有容器CPU配额（4），用于验证和后续采集。有效环境变量写入每题 `isolation.json`，旧失败验证和日志保留。该变更影响实际工具执行环境及耗时，不能声称前后环境完全相同；不改变模型参数、轮次或预算。

第81题的环境依赖下载正常但缓慢，原有单次镜像构建30分钟时限在SciPy下载期间触发，仍未调用API。为落实用户不设置任意任务时限、继续运行的要求，当前配置增加 `image_preparation_time_limits_enabled=false`，同时关闭镜像构建30分钟和外层准备65分钟时限。其他配置默认保留这两项限制；容器资源和隔离约束不变。原失败日志和构建日志保留，仍运行同一固定样本。

第81题重试完成镜像构建后，原始SWE-bench配方的pandas 2.0.0与该提交的seaborn 0.12不兼容：legacy lineplot和objects绘图均调用已移除的 `mode.use_inf_as_null`。两题目标分别为layout参数命名和wrapped pair plot标签可见性，不是pandas兼容性。因此只对该repo/version且原配方固定pandas 2.0.0的任务，在任务镜像准备中执行 `python -m pip install --no-deps pandas==1.5.3`。不改官方配方记录、不改题目源码、不升级其他依赖；实际覆盖命令和包版本保存于task-commands/pip-freeze和环境归档。失败的原pandas 2.0.0任务镜像先完整归档再释放，保留共用依赖层。必须披露这是相对原始SWE-bench配方的环境兼容性偏离。

第84题发现单提交浅克隆缺少版本标签，setuptools_scm因此将pytest识别为 `0.1.dev1+g97ed533f6`，低于项目声明的最低版本2.0，验证失败。修复是补齐固定base_commit的祖先历史和指向祖先的原始版本标签，而不是修改源码、最低版本要求或伪造PRETEND_VERSION。打包前验证所有提交均为base_commit祖先、无远端配置、无不可达对象；原浅克隆源码包和失败镜像完整归档。该提交真实git describe为 `8.0.0.dev0-82-g97ed533f6`。后续pytest样本逐题使用同一历史范围校验，不把后续修复提交带入题目环境。源码修订记录位于运行目录的source-cache-revisions.jsonl。

第99、100题的xarray也使用setuptools_scm（其声明的fallback_version为999），因此在采集前按相同原则补齐各自base_commit的祖先标签。两题git describe分别为 `v2022.06.0-36-g790a444b`、`v2022.06.0rc0-45-gf045401c`；仍只包含各自提交及祖先，不包含另一题的后续提交。原浅克隆包单独备份，源码树不变。

第99题首次依赖构建在libmamba求解时触发4GiB构建容器的OOM，Docker的oom/die/destroy事件及完整失败日志保留，尚未调用API。仅将xarray的依赖环境构建内存及memory-swap总量提高到16GiB，仍使用2CPU；任务镜像构建仍为4GiB，实际采集仍为4CPU/8GiB/pids256。没有改变依赖配方、题目源码、模型或轮次。构建调用参数和资源配额另存build-invocation.json，成功镜像记录中也保存build_resources；历史记录不覆盖。

第99题第二次构建通过求解，但原配方先安装未固定版本的Conda全依赖、随后用pip降级核心包，导致distributed/dask、pytest-env/pytest、rasterio/numpy、iris、statsmodels、wheel/packaging、预装xarray、zarr等冲突，pip check失败。后续将官方pip固定版本提前纳入Conda及嵌套pip求解，不删可选依赖、不跳过pip check；额外固定distributed=2022.8.1匹配官方dask、wheel=0.45.1兼容packaging23.1，并用早于两题提交的xarray2022.3.0作为依赖求解的临时占位包。任务镜像仍从各自base_commit安装真实源码，替换该占位包；占位版本不充当目标仓库版本。以上额外约束属于依赖兼容性修订，必须在复现实验中披露，原官方配方和失败日志均保留。

第99题第三次构建的pip check仅剩rasterio 1.4.3要求numpy>=1.24的问题：Conda求解允许它与官方numpy1.23.0共存，但Python包元数据不允许。核对PyPI的rasterio1.3.9元数据后，额外在Conda/PIP约束中固定rasterio1.3.9；保存原始PyPI元数据和本次失败证据，不删除rasterio、不改变官方numpy固定版本。该附加版本约束同样属于需要披露的兼容性修订。
