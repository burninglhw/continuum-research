## 4. 转换时必须遵守的规则

### 4.1 请求身份与分组

1. 先限定 project、原始 session 文件和分支，再处理 requestId/message.id。
2. 对一致的请求合并 assistant 分块，按 tool_use_id 去重并保留所有工具。
3. 不累加每个快照重复报告的 usage；保留原值、变化轨迹和来源行号。
4. 多 message.id、usage 冲突、身份缺失、sidechain 单独标记；不能默默套用 last-event-wins。
5. 通过 parentUuid、工具结果关联和会话内记录次序校验因果关系，时间戳只能作为辅助。

### 4.2 上下文和输出长度

在这里的数据格式下，报告的 prompt 长度按下式计算：

`reported_prompt_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens`

不要重复加 `cache_creation` 的内部细分字段。所有长度保留 `reported_` 前缀，表示来源模型的计数。

这些是 Claude usage 的 token 数，不是同一真实文本在 Llama/Qwen tokenizer 下必然相等的长度。可以让目标模型接收相同“数量”的合成 token，以形成长度控制实验，但必须标明这种长度映射。

`output_tokens` 先按日志原样保留，不能因为数值小就擅自补到 128/256，也不能把最后记录当成完整 decode 的确证。联系作者或找更完整 usage 前，只能称“按报告长度回放”；若加入固定 decode 长度，必须作为单独的合成敏感性设置。

同样，不建议直接删掉所有 stop_reason 缺失的记录：这会删除绝大多数数据，造成强烈选择偏差。缺失需要报告和解释，而不是用一个过滤条件隐藏。

### 4.3 prefix 不能从 cache_read 还原

`cache_read_input_tokens` 是原服务商缓存计费/命中计数，受缓存策略、breakpoint、TTL、共享 system prefix 等影响。它不等于相邻请求最长公共前缀，更不等于 H200 回放中的实际 KV 命中。

公开文本已脱敏，所以不能精确恢复原 token IDs、跨请求共享位置及完整压缩操作。建议用明确命名的假设做实验：

- **Append-only 高复用场景**：上下文未收缩时尽可能保留上一轮输入及输出；这是高复用假设，不是实测真相。
- **部分复用场景**：对可保留前缀分别采用 50% 和 0% 等预声明比例，检查收益是否依赖极端高复用。
- **收缩/重置场景**：遇到长度下降或已识别的重置另起前缀版本；如研究部分保留，另列设置，不能猜测真实截断位置。

实现要求：按目标模型合法的非特殊 token IDs 构造，固定 seed；每个独立 program 的首个缓存块做命名空间隔离，校验没有意外跨 program 前缀。不能重复同一个字符串来“凑长度”，也不能每轮重新随机生成整段 prompt。

下一轮应包含约定保留的上一轮输出 token。所有策略须共享相同 token 序列和长度；固定 output 长度不等于固定 output 内容。若采用实际贪心输出并反馈到下一轮，需要逐轮检查不同策略的 token hash 一致性，否则不是严格的配对 workload。若使用强制固定输出序列的回放接口，所有策略采用同一接口并报告额外开销。

### 4.4 人类停顿和 program 边界

建议身份为 `project/session/branch/episode`，而不是单独的 session_id。

- 普通 user 输入、人工审批和恢复需结合事件类型及父子链识别；tool_result 不算新的人类输入，meta 记录也不能直接算。
- 人为闲置不进入工具历史分布，不让 KV 在人工暂停期无限 pin。
- 恢复后的 episode 仍使用日志里的长历史上下文长度，不能把它重置为短 prompt。
- 不因等待超过某个秒数就自动判作 human pause；例如长 Bash 可能是真任务，也可能含审批，公开记录未必足以区分。
- 第一版只纳入能解释为单主链的 episode；子代理并发和复杂 DAG 留作独立扩展，报告排除比例。

### 4.5 工具时间和多工具

官方 parser 的时间主要来自 `result_timestamp - tool_use 所在 assistant 记录的 timestamp`。它是日志观测延迟，可能包含审批、输出记录、通信或恢复间隔，不是专门的工具计时器。

第一版建议只用结果关联明确的**单工具 transition**，采用非流式阶段回放：本轮 LLM 完成后，等待对应的观测延迟，再发下一轮。这是将观测延迟映射到新推理服务的明确假设，不声称复原原 Claude streaming 时间线。

多工具版必须保留每个工具的发出和结果时间、依赖关系，用统一参考点计算整个 barrier。不能直接累加 duration，也不能在工具起点不同的情况下直接取 `max(duration)`；仅取最后结果的绝对时间也不足以定义等待时长。

特别注意：最后 assistant 快照不一定是精确的 LLM 完成时刻；部分工具可能和流式生成重叠。缺乏可信完成时间时不能宣称得到精确的“LLM 完成后剩余工具等待”，也不能把负值静默钳成零。复杂重叠先隔离，或另列明确的相位重映射实验。

工具结果多次出现时先分辨重放、分支和历史复制，不能无条件选最后一次。49 小时等长尾保留在原数据中；小规模实验可以预先声明不纳入某类异常/超长样本，但不能偷偷把它们缩成几秒。

### 4.6 预测信息隔离

- 脱敏后 Bash 参数不可恢复，只能用 `Bash`、`Read`、`Grep` 等公开 tool name，不能编造 pytest/git/python 标签。
- 当前轮已经发出的工具类型可传给调度器；本轮将等待多久属于未来结果，只能由回放器掌握。
- 历史统计只使用训练集，或本次运行中已经结束的工具样本；禁止读取测试 trace 的未来 duration 来计算 TTL。
- Oracle 可以单独实现并明确命名，但不是 Continuum 正常基线。
- train/test 按原始 session 分组，先分组再切 episode；同一原始 session 的分段不能分到两边。另可做 project-held-out 泛化测试。

## 6. 论文口径与指标

CacheWise §6.1 使用 2×H200、TP=2、Qwen2.5-Coder-32B-Instruct、chunked prefill 最大 512 tokens，随机 80% sessions 训练预测器，其余测试。人工闲置作为 session boundary，恢复后保留长历史上下文。

**这并不意味着用它的数据测 Continuum 必须改成 32B/双卡。** 可以先沿用已经准备的 Llama-3.1-8B 类配置做机制验证，明确模型和硬件差异；不要把这种结果说成 CacheWise 原图复现。

CacheWise §6 Metrics 明确把 session completion time 定义为各次 LLM request latency 之和，**排除工具耗时**。不能把它与含工具时间的端到端 JCT 混为一谈。

建议同时报告：

| 指标 | 定义/注意事项 |
|---|---|
| E2E episode JCT | 从首请求提交到最后请求完成，含调度/排队和工具等待，不含切段去掉的人工闲置 |
| Serving-only completion time | 同一 episode 各轮 request 提交至完成的 latency 之和；含服务排队、不含工具等待 |
| TTFT P50/P95/P99 | 观察排队与 prefill 的用户可见影响 |
| KV 命中 / 重算 prefill tokens | 由当前回放服务实际测量，不能用源日志 cache_read 冒充 |
| Eviction / preemption / transfer bytes | transfer 只在确实启用 CPU offload 等搬运时统计，区别于丢弃重算 |
| 吞吐 / token goodput | 明确有效新 token 与重复重算 token 的计数规则 |
| 调度开销、尾延迟、公平性 | 防止均值下降但新 program 被长期饿死 |

在两阶段、相同固定工具延迟的回放中，工具等待越长，E2E 加速越可能被稀释；serving-only 收益可能明显，但它不等于同倍数的端到端收益。两张图应分别画。

沿用此前暂停 GPU 实验的约束，先确认有可用卡以及获准使用。此阶段不需要重新跑真实软件仓库/pytest，因此不需要每道题一套 SWE-bench 容器。

建议预先声明的 pilot：

- 从隔离好的测试集中选 8 个完整、单主链、多轮 episode，尽量来自不同原始 session；不足则报告实际数量。
- 初步只接收结果关联明确的单工具 transition；完整 episode 的 prompt+output 均不超模型限制。
- 可设置完整 episode 轮数 2–20、单次观测工具延迟不超过 60 秒作为**冒烟子集筛选**。必须报告筛掉多少；不是把长耗时裁剪为 60 秒，也不是完整数据集结论。
- 并发先测 1/2/4/8，所有方法使用相同 episode、token 序列、工具等待、模型权重、dtype、TP、batch 配置、KV cache 容量和随机种子。
- 明确控制冷/热 prefix cache 和估计器状态；训练得到的初始统计相同，每次重复重置，不能让后跑的方法享受前一方法预热。
- 检查真正发生工具 metadata 传递、pin/unpin、KV hit 和 eviction。没有发生缓存竞争时，收益接近零是正常结果。
- 每个设置至少重复 3 次，交错运行方法顺序，记录 GPU 干扰。pilot 只做方向性验证，不因样本小就夸大显著性。
